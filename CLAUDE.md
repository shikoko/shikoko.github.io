# Working on shikoko.github.io

This repository is Bogdan Roatis's site, published at https://shikoko.github.io/. It has two pages:

- **The home page**, `index.html` with `assets/css/home.css` on top of `assets/css/resume.css`: his projects and the apps he's worked on. Its pictures, loops and icons are in `assets/work/`.
- **The CV**, `cv/index.html` with `assets/css/resume.css`, at https://shikoko.github.io/cv/.

Both share the theme button's script, `assets/js/theme.js`. The **Deploy** workflow (`.github/workflows/deploy.yml`) builds the site with `npm run build` on every push to `main` and publishes it with GitHub Pages. The build renders two files from the CV with Chromium: `Bogdan-Roatis-CV.pdf`, the copy the Download PDF buttons save, and `assets/social-preview.png`, the picture shown when either page is shared. Neither is committed. Tributary (`/tributary/`) and Signature (`/signature/`) are published from their own repositories, so the home page links to them by their full addresses.

## Branches

- **One branch per change**, made from the latest `main`, and named after what the change does: short, lowercase, words joined by hyphens, no prefix. For example `tributary-project`, `stem-end-date`, `pdf-link-text`. Two unrelated changes get two branches.
- **Don't use the `claude/…` branch a cloud session is given** (names like `claude/intelligent-davinci-vajqt0`). Make the branch named after the change instead, and push that one. If the change grows into something else, rename the branch to match before pushing.
- **`main` only changes through a pull request** from a change's branch, because whatever is on `main` is live. Merge it with a merge commit, never "Squash and merge" or "Rebase and merge".
- **Rebase before merging:** rebase the branch onto the latest `main` and push it with `--force-with-lease`, so the graph shows a short loop that joins straight back in.
- **Delete the branch once it's merged.**

## Commits and pull requests

- **No attribution lines, anywhere.** No "Co-Authored-By: Claude", "Claude-Session:", "Generated with Claude Code", "Generated by Claude Code" or similar, in commit messages, pull request titles or descriptions, or comments. `.claude/settings.json` turns off the ones Claude Code adds by itself.
- **Always remove the "Generated by Claude Code" footer.** A pull request opened or edited from a Claude Code cloud session gets a `---` line and "_Generated by [Claude Code](…)_" added to the end of its description, and it comes back after every edit made from there. The **Tidy pull requests** workflow (`.github/workflows/tidy-pull-requests.yml`) removes it within a minute. After opening or editing a pull request, check that the footer is gone.
- **Commits are the owner's.** Author and committer are the repository's owner, never Claude, and commits from a cloud session aren't signed with the session's key. Before committing in a cloud session, set this in the clone's own config (not the global one):

  ```bash
  git config user.name "$(git log -1 --no-merges --format=%an origin/main)"
  git config user.email "$(git log -1 --no-merges --format=%ae origin/main)"
  git config commit.gpgsign false
  ```

## Writing commit messages and pull request descriptions

Commits go out under the owner's name and are public, so they get quoted out of context. Write them as an experienced engineer would.

- **Only facts about the change.** Plain terms: what changed and why. No commentary or chatty asides, and nothing that sounds unsure.
- **Every sentence should read well quoted on its own.**
- **Mention side effects** (a bumped stylesheet version, a changed social preview card) in a final line.

### Commit messages

- **Subject:** imperative, specific, under 72 characters: "Mark the STEM role as ended in September 2026", not "CV updates".
- **Body:** what changed and why, wrapped at 72 columns. Name the sections, roles or styles that changed.

### Pull request descriptions

- **Start with the problem** in one or two sentences: what was wrong or missing on the CV.
- **Changes:** a short list of what the pull request does.
- **Checked:** how the page and the built PDF were checked (screen widths, light and dark, `npm run build`), and anything that couldn't be checked, with the reason.

## Changing the CV

- **Only facts the owner has confirmed.** Don't add claims, numbers or technologies that aren't already on the CV or given by the owner. Ask when unsure.
- **Build the site and look at it before committing.** `npm run build` (`tools/build.cjs`) builds it into `build/site/` exactly as the Deploy workflow does: it copies the pages and their assets, checks that every file they link to is there, renders `Bogdan-Roatis-CV.pdf` and `assets/social-preview.png`, and fails if the PDF is longer than three A4 pages or the fonts (Google Sans, JetBrains Mono) didn't load. Open the PDF and check nothing is cut off. In a Claude Code cloud session Playwright is already installed; elsewhere, run `npm ci` and `npx playwright install chromium` first. `build/` is ignored, so nothing it makes is committed.
- **The workflow builds every pull request too**, so one that makes the PDF longer than three pages fails its checks. Wait for the build to pass before merging.
- **Keep the social preview in step with the page.** The card is `tools/social-card.html`, and it repeats the title under the name and the most recent roles. When those change on the page, change the card and its `og:image:alt` text in `cv/index.html` and `index.html` to match. The build also writes `build/github-social-preview.png`, the same card at 1280×640 for the repository's own social preview on GitHub (**Settings → General → Social preview**). That one can only be uploaded by hand, so give it to the owner when the card changes.
- **Bump the version in the link** whenever a stylesheet or script changes, so visitors don't get a cached copy: `resume.css?v=…` in both `index.html` and `cv/index.html`, `home.css?v=…` in `index.html`, and `theme.js?v=…` in both.
- **Check the page** at phone, tablet and desktop widths, in light and dark, before committing.

## Changing the home page

- **The same facts as the CV.** Descriptions, roles and years on the home page come from the CV or from the owner. When a role or an app changes on the CV, change it here too.
- **Projects** are shown like the image at the top of their README: the icon, the name and one line on the left, and a crop of the app's window coming in from the right. The crop is a WebP about 960 pixels wide in `assets/work/`.
- **The STEM apps** share one black band under STEM's name, and each has a short loop: a silent H.264 MP4 of a few hundred KB, with a JPEG still frame from it as its poster. The band is true black, and so is each video's background: bring a video's near-black down to 0 when encoding it (ffmpeg's `colorlevels`, as below), or its rectangle shows on bright and HDR screens. Each loop also fades out in a soft oval into the band. Under each app's role and years, a "Video by" line credits who filmed its loop, linked to their profile. The page plays a loop only while it's on screen, and never with reduced motion, when the still shows instead. Make a loop from a video or GIF with ffmpeg, for example `ffmpeg -i in.mp4 -an -vf colorlevels=rimin=0.045:gimin=0.045:bimin=0.045 -c:v libx264 -crf 25 -pix_fmt yuv420p -colorspace bt709 -color_primaries bt709 -color_trc bt709 -movflags +faststart out.mp4`, and bump the `?v=` on its `src` and `poster`. Originals aren't committed.
- **Other apps** are rows with their store icon, a 128-pixel PNG in `assets/work/icons/`. An app with no store listing gets a lettered tile instead.
- **Links** to the projects use their full addresses, since they aren't files of this site; the build fails if any other link points to a file that isn't there.

## Design

The CV's design is below. The home page uses the same colours, type, header and section labels, with dark surfaces for the work: the project cards and the STEM band keep their colours in both themes, because they carry the apps' own dark screens and videos.

- **Minimal and editorial:** a cream page, near-black text and one ink-blue accent. Google Sans for everything: the name, headings (semibold for organisation and role names) and all running text, with dates in smaller grey type; JetBrains Mono only for section labels and the contact labels.
- **Readable greys:** secondary text uses `--muted`, which keeps at least 7:1 contrast (WCAG AAA) in both themes and in print.
- **Space separates things, not lines.** The only drawn lines are the vertical rule between each entry's left column (organisation, dates, links) and its details. Don't add borders, cards, badges, timelines or decorative icons.
- **Every role is shown in full.** Nothing folds away or is shortened to save space; the most recent roles come first and simply have the most to say.
- **No skill ratings,** percentages or progress bars: skills are plain lists under a few categories.
- **Light and dark:** the page follows the system setting until the theme button in the header picks one, which is remembered on that device. Switching reveals the new theme in a circle growing from the button while its moon and sun icons turn into each other; with reduced motion, or in browsers without view transitions, it switches at once. Print and the PDF are always light.
